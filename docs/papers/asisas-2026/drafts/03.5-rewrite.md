## 3.5 Security and trust

Security here covers four things in declining order of strength: authorisation, auditability, scoring trust, and what we have not yet built.

**Authorisation** is currently shared-secret. The PostGraphile endpoint is gated by a single `x-hasura-admin-secret` header check in an Express middleware in front of `postgraphile()`; anyone with that secret has full read/write access to the schema. We do not use PostgreSQL row-level security: `pg_policies` is empty and no table has `rowsecurity` enabled. User-level authz is enforced one layer up, by restricting which Kubernetes workloads carry the secret. Admin actions inside the bot are gated by an `admins` table with `granted_by` and `granted_at` columns, seeded with a root admin from the `ADMIN_EMAIL` environment variable on bot startup. That table is a permissions check inside the bot, not an authorisation boundary against the GraphQL surface.

**Auditability** is partial. Every LLM call has a named entry point in the codebase (`extract`, `extract_deep`, `score`, `triage`, `arbitrate`, `respond_as_seth`, `weave_signal`) and a model assignment that is either hardcoded (triage and arbitration on Anthropic) or set from config and passed in as a parameter (Scaleway calls). The `ingestion_log` table records per-source content hashes and per-table record counts for every ingestion run, so an extraction can be traced to the source document and the run that produced it. Prompt context and raw judge scores are not persisted: only the median of the three judge scores is stored as the record's `confidence`. The substrate can be dumped to JSON via `mothertree dump` and restored via `mothertree restore`; both are manual operator commands rather than automatic pre-consolidation snapshots, which we treat as a gap to be closed.

**Trust in extracted records** is enforced at the data layer by the multi-judge quorum described in §3.2. The failure mode the panel guards against is single-model bias; the failure mode it does not guard against is judge collusion (all three agreeing on a plausible-but-wrong record). The current implementation marks such records as `flagged=True` in the database and leaves them in the table. There is no review queue, no Slack notification to a reviewer channel, and no rolling sample of auto-accepted records into a review surface. Building a human-in-the-loop review path on top of the flag is open work, named here so the gap is visible.

**What we have not yet built.** Consent for passive signal capture in Slack channels is not in the system: the `users` table has no consent column, no consent ask runs on first contact, and the Spotter looks at every message in every channel the bot is in. Designing and shipping that consent flow is the largest item of trust work we owe the deployment, and we flag it here as a known gap rather than a feature.

**What is in place.** Containers run as non-root (`USER 1000:1000` in `Dockerfile.bot` and `Dockerfile.jobs`); secrets are SOPS age-encrypted with the private age key in 1Password and in a sealed Kubernetes secret in `flux-system` so that Flux can decrypt at reconciliation; backups go to Scaleway Object Storage at `s3.fr-par.scw.cloud`, the same Paris region the cluster runs in. External URL fetches in the ingestion and bot pipelines use `httpx.get` with timeouts and size limits but no SSRF protection, so internal cluster endpoints are reachable from any operator-controlled URL the bot is asked to fetch; adversarial Slack input has not been penetration-tested. These last two are named, not deferred.
